## Book rule implemented

- R9, LONG-TERM COUNTDOWNS (CB p.164): "decide how far out the event should be (usually between 4 and 12 ticks) and, on a piece of paper, create small boxes for each tick. Starting from the first and working towards the last, write some events that may occur along the way that foreshadow the final event. These steps can alternate between softer and harder moves" / "During a long rest, you should generally tick down a relevant long-term countdown once." The book's example tracker has a line per value 8 … 0, the 0 line the final event, with '*' on the steps where news reaches the party.
- Page check: quoted as re-checked by K0 and K2 on 2026-10-21 (printed p.164 = PDF page 165). This worktree has no pdfjs-dist and the Core Book PDF is over the reader's 100 MB limit, so K4 did not re-open it.

## Server

- `convex/countdownTracks.ts` (new):
  - `setStep` (keyedGmMutation `{ campaignId, countdownId, value, text, news? }` → `{ steps }`): writes one step through `validateSteps` (trimmed, 1-200 characters, one per value, 0..start); empty text removes the step. NOT_FOUND for a frame-owned or another campaign's countdown; COUNTDOWN_RULE for a countdown that is not long-term, a cancelled one, a value outside 0..start or text over 200.
  - `setRestMode` (keyedGmMutation `{ campaignId, countdownId, restMode: "auto" | "remind" }` → `{ restMode }`): the Q3 switch. Same refusals.
  - `afterRest` (gmQuery `{ campaignId }`): for the latest rest when it is a finished long rest, `{ restId, lines: [{ countdownId, name, currentValue, line }], reminders: [{ countdownId, name, currentValue }] }`; lines come from the unreverted `countdownTicks` rows keyed on the rest's campaign row; reminders are the armed, active long-term countdowns set to Reminder that this rest has not ticked. null otherwise.
  - `tickOnRest` (keyedGmMutation `{ campaignId, restId, countdownId }` → `{ currentValue, status, line }`): the reminder's one-click tick, through `applyTick` with source "rest" and the rest's campaign row as entryId, so the rest's undo takes it back. NOT_FOUND for another campaign's rest or countdown (or a frame-owned one); COUNTDOWN_RULE when the rest is not the latest finished long rest (an older, short or interrupted rest), the countdown is not long-term or not active, or this rest already ticked it (D5).
  - `tickLongTermOnRest` (helper, not a function) and `trackLine` ("Invasion: 5 left - <step>", "Invasion: final event - <step>", "(news reaches the party)" on a news step).
- `convex/rests.ts`: `applyRest` keeps the campaign row's id; after every existing effect and both log writes, a finished long rest (not `interrupt`, not a short rest) ticks each armed, active long-term dashboard countdown set to Automatic once (`by_campaign_armed`, bounded) through `applyTick` (source "rest", entryId = the rest's campaign row). When something ticked or reminds, one GM-only row (kind "countdown", visibility "gm", in the rest's group, undoable) says "Long rest: Invasion: 7 left - …; Reminder: tick Plague?". The finish result gains optional `countdownLines` (only when something ticked, so existing `toEqual` results are unchanged). `rests.undo` takes the ticks back through K0's `undoEntry` → `revertTicks` (the campaign row is in the group) and marks the GM row undone with the group. The public rest rows never carry step text or countdown names.
- Armed and the switch combine as: not armed → long rests leave it alone; armed + Automatic → ticks once per finished long rest; armed + Reminder → only reminds. A trigger at 0 also writes K0's own trigger notice with the consequence.

## Deviations and notes

- `useKeyed` moved from `card.tsx` to `track.tsx` (exported; both use it) so the card and the track share it without an import cycle.
- The plan's acceptance wording for armed ("Tick on every long rest") and the Q3 switch are both kept: armed decides whether long rests concern the countdown at all, the switch decides tick or reminder.
- The GM notice is skipped for a party at the rest cap (49 PCs), where one more row would push the rest's undo group past 50.
- Pre-existing, not K4: `tests/e2e/countdown-rolls.spec.ts` (K1) fails on this base because K2's dialog creates countdowns armed by default, so the roll ticks the card before the feed button (expects 4/4, gets 3/4). K4 does not touch that path (the armed default is K2's `useState(true)`, unchanged here); the fix belongs to K1's spec (uncheck the armed box) or to the orchestrator.
